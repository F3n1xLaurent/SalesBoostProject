13 ноября 2026. Исходный звонок: `pipecat-controller-6`. Запрошена жёсткая проверка: не задавать заново уже произнесённый вопрос.

## Причины повторов

Вопрос о скидке в этом звонке прозвучал один раз. Однако остался второй путь постановки вопросов: после вопроса контроллера native Realtime мог сам сформулировать уточнение того же вопроса. Оно не учитывалось в `asked_topics`, поскольку не имело явного ID обязательного вопроса. Проверки только счётчика подготовленных вопросов поэтому не охватывали все источники речи.

Например, после вопроса о сроке владения менеджер начал фрагмент «Тогда». Его ошибочно приняли за законченный непонятный ответ. Realtime повторил вопрос о сроке владения. События `assistant_response` с одним и тем же native response ID и статусами completed/cancelled — это обновления одного ответа, а не доказательство двух отдельных воспроизведений. В журнале при этом есть начатый TTS-контекст повторного native-вопроса.

Повтор вопроса о пробеге был вызван просьбой менеджера напомнить, что клиент хотел уточнить. Новый запрос пользователя требует более строгого поведения и для этого пути: повторная постановка того же вопроса блокируется.

Native-уточнение про пороги также теряло ссылку на обязательный вопрос. Затем понятный ответ с приглашением оценивался как недостаточный, а после двух уточнений тема автоматически получала `unknown`. Такое закрытие темы не доказывало получения ответа.

## Жёсткая защита

- У каждого вопроса плана есть ID `plan:<key>`, постоянный в пределах звонка. Формулировка, добавленное имя, подтверждение визита в той же реплике и другой путь вызова не меняют этот ID.
- Проверка и резервирование происходят до первого ожидания синтеза/провайдера. Две одновременные попытки не могут отправить один вопрос дважды.
- Перед постановкой аудио в очередь ID фиксируется в журнале вопросов; после успешной постановки получает состояние queued. Даже отмена задачи в момент постановки не снимает защиту. Отмена до попытки поставить аудио освобождает временную резервацию.
- Это консервативная граница: блокировка начинается уже при попытке поставить аудио в очередь, раньше доказанного звучания на линии. Отсутствие playback ACK само по себе не разрешает повтор.
- Для вопросов дня и времени есть общие ID полей: смена подготовленной формулировки не обходит защиту. Предложение конкретного слота имеет отдельный ID по дню и времени; другой слот можно предложить, тот же слот повторно спросить нельзя.
- Realtime больше не ставит собственных вопросов. Ветка непонятного ответа не просит модель переформулировать вопрос плана; фильтр перед TTS исключает native-вопросы, включая типичные вопросительные конструкции без `?`.
- Если native-вопрос был отфильтрован, путь восстановления также проходит через общий запрет и не воспроизводит тот же подготовленный вопрос.
- При блокировке тема не становится отвеченной и не исчезает из обязательных. Непонятный ответ допускает одну нейтральную просьбу повторить ответ; дальнейшая неопределённость оставляет тему открытой вместо автоматического `unknown`.
- Нейтральные вводные фрагменты, в том числе комбинации с именем клиента, не запускают генерацию нового вопроса.
- Жалоба на связь после вопроса вызывает короткое «Я на связи», без повторной постановки того же вопроса. В составной реплике блокировка вопроса сохраняет отдельно подготовленный ответ на обращение менеджера, например имя.

Диагностика: `controller_question_blocked` содержит ID, текст и причину блокировки; `controller_wait` объясняет ожидание. Состояние `question_ledger` сохраняется в отчёте звонка отдельно от ответов и CRM-фактов.
