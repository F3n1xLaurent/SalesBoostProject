# Автотестирование

`/testing` разделена на два таба:

- `Гипотезы` — прежние изолированные телефонные эксперименты;
- `Автотестирование` (`/testing?tab=autotesting`) — проверки без набора номера.

Направления задаются каталогом `GET /api/admin/auto-testing/catalog` со стабильными
ID `call_plan`, `report`, `trainer`. Все три направления доступны при
настроенных API соответствующего контура.

## Что именно проверяется

Регрессия `8cfa445a-0049-4256-bcc6-de7773f7faf8` (30.10.2026): в общей
Realtime-цепочке плана/гипотезы добавлены напоминания из реально произнесённых
реплик: максимум одно уточнение одной темы, один дополнительный пункт (включая
совпадение с обязательным вопросом), сохранение неотвеченного вопроса при
исправлении имени. Эти семантические правила модели требуют повторного живого
прогона; модульные проверки не доказывают поведение модели.
Отдельная серверная защита конкретного предложения визита не принимает
`end_call.reason` за произнесённое подтверждение. Текст на этой точке буферизуется
до завершения ответа; голое прощание не передаётся в TTS, один раз запрашивается
исправление, затем при повторном нарушении задаётся короткое уточнение без
hangup. Подтверждение и прощание проходят одним ответом; завершение по-прежнему
следует сразу за фактическим окончанием воспроизведения.

Исправлены и фикстуры: менеджер отвечает на вопрос о запаске по существу,
а кейс смены модели/года после исправления имени содержит прямой ответ на
расхождение года, чтобы проверять и уточнение, и принятие полного ответа.
Версия фикстур входит в снимок и хеш конфигурации: сравнение нового набора со
старым не объявляется доказанным исправлением при изменившемся покрытии.

Новый запуск использует **текущую серверную** `OPENAI_REALTIME_MODEL`, актуальный
промпт выбранного плана, выбор профиля/предмета и голос как при обычном звонке.
Проверяются общие механизмы диалога, VAD, функций, TTS и воспроизведения по
эмулируемому протоколу Voximplant. `createCallPlanSimulation` использует ту же
фабрику production-сессии и preflight, включая повторные подключения, что
`prepareProductionOpenAiRealtimeCall`. Ни `StartScenarios`, ни `prepareCallPlanTelephony`
не вызываются: номера не набираются, записи звонков/расписания/обычные оценки
не создаются. Результаты хранятся отдельно в `storage/realtime-regression`.

Фикстуры отдельных сценариев могут задавать специальную легенду, например
женский род; это не меняет исходный план. Модель из вкладки «Гипотезы» не
используется. Если основная телефония переключена на `elevenlabs_agent`, запуск
блокируется с объяснением, вместо проверки другого движка под видом основного.

Это не проверка всей телефонии: реальная PSTN-сеть, буферы Voximplant,
автозапуск расписания и генерация обычного отчёта не сертифицируются эмуляцией.
Качество звука/ударения остаются `review` для прослушивания. Полный `pass`
требует полного покрытия релевантных сценариев; прерванные/непроверенные пункты
не становятся зелёными. Тренировки и отчёты проверяются отдельными наборами ниже.

## Автотестирование отчётов звонка и тренажёра

Адрес: `/testing?tab=autotesting&target=report`. Основание — PDF
«Чек-лист: расшифровка и отчёт тренажёра», все **29 пунктов** в исходном
порядке, включая SAL-1–9. Критерии, правила и вымышленные диалоги заданы в
`src/testing/reportTestCatalog.ts`, версия набора `2026-10-30.1`.
Ничего выбирать из реальных звонков или тренировок сотрудников не требуется.

Пять групп: расшифровка (1–4), оценка реплик (5–11), примеры «Как лучше»
(12–19), находки/итог (20–26), интерфейс/регрессия (27–29).
Шесть кейсов × два источника = 12 сценариев:

- сильный ответ, конкретные суммы/выгода и визит;
- спорное распознавание года в длинном содержательном ответе;
- односложное «Ждём» без закрепления адреса, времени и контакта;
- дождь, снег, грязь на датчиках и гарантия: несколько условий вопроса;
- подмена имени, модели и года;
- Zeekr/Coolray/Esteo/Exlantix/Volga, суммы и сильные стороны с пробелом.

Запуск вызывает реальный `evaluateSessionV2`, затем для звонка
`generateCallAnalyticsBundle`, для тренажёра `generateUnifiedTrainerReport`,
включая их обычные нормализаторы и исправление примеров/находок.
Эталонные ожидания передаются только независимому оценщику теста, а не
генератору отчёта. Итог не подменяется готовым «правильным» JSON.
Справочник проблем читается как в обычном отчёте. Модель, справочник, версия
и хеш фикстур входят в снимок условий проверки.

Это тест **текстового анализа и генерации единого отчёта**, не всей цепочки
сохранения/загрузки записи. Нет звонка, TTS, записи в TrainerSession/CallHistory,
изменения баллов сотрудников, уведомлений или финализации обычной тренировки.
Условия сценария/`plan_criteria`, кастомные корпоративные чеклисты и доставка
отчёта через production API этим набором не сертифицируются.
Обычные prompts/скоринг не меняются при добавлении тестов; найденные ошибки
показываются как ошибки, а не исправляются специально для эталона.

Детерминированные проверки: роли/текст/порядок, наличие меток/комментариев,
примеры у normal/negative, противоречие positive и негативной находки,
разные примеры одной реплики, точные дубли, балл/вердикт/пять категорий.
Остальное оценивает модель по конкретным критериям. Для `pass`/`fail` нужны
реальные индексы реплик **менеджера**, точные значения и JSON Pointer полей
сгенерированного отчёта/оценки. Невалидная ссылка, неверная роль, недоступный
оценщик или недостаточные свидетельства дают `review`, не `pass`.

Границы покрытия видны в интерфейсе:

- 1, 2 и 4: проверяется текстовая часть, но без исходного аудио точность ASR и
  реального разделения говорящих остаётся `review` (найденная ошибка — `fail`).
  Для звонка спорный кейс подаёт original/reviewed ASR, как production;
  тренажёр получает спорный исходный вариант, как его текущая цепочка.
- 27: hover/tap подсказки (i) требует отдельной браузерной проверки — `review`.
- 29: вход и результат SAL-кейса сохраняются; наличие архива само по себе не
  доказывает, что историческая ошибка исправлена. Для подтверждения есть
  повтор кейса, базовый запуск и сравнение конкретных критериев; пункт остаётся
  `review` для контроля регрессионного набора.

Можно повторить всю серию, один кейс (например `trainer-closing`) или один
пункт (например `report-single-example`). При выборе пункта генерация выполняется
только для соответствующих кейсов, оценщик проверяет только выбранные критерии.
Частичное покрытие сценариев не становится полным зелёным результатом.

После разбора `3bc8ef34-2a48-423a-afd8-4ecb465456d8` оценщик имеет версию
`report-2026-10-30.2`; в снимок настроек входит хеш общих правил генерации.
Исправления действуют в обычных генераторах звонка **и** тренировки, не только
в тестовом контуре:

- Частный пробел не превращает содержательную реплику автоматически в negative.
  При нескольких подтверждённых выполненных действиях и некритичном замечании
  используется normal, с достоинствами и конкретным пробелом в комментарии.
  Подмена имени/фактов, грубость и отсутствие прямого ответа не смягчаются этим
  правилом. Для normal сохраняются подтверждённые сильные действия.
- «Как лучше» генерируется для всей реплики с учётом всех её находок, одинаково
  в карточках и транскрипте. Совпадение примеров разных проблем не удаляет
  сами проблемы. Потеря правильных чисел, условной выгоды «до», несколько
  вопросов или повторное «Чем помочь?» при известном запросе требуют ремонта.
  Числовые эквиваленты «300 тысяч» / «300 000» допускаются.
- Примеры normal/negative ремонтируются и без отдельной карточки находки;
  интерфейс не прячет пример у normal. Резюме нового отчёта строится из итоговых
  находок и подтверждённых сильных сторон; основной неотвеченный вопрос/подмена
  фактов приоритетнее второстепенных замечаний. Архивы не перезаписываются.
- Пустой, обрезанный или неполный JSON отчёта получает максимум две попытки
  (10/16 тысяч токенов с учётом reasoning). Неполный чек-лист оценщика не
  превращается в all-NO. HTTP 401/402/403/404 сохраняются как технические ошибки
  и останавливают серию; оставшиеся сценарии не запускаются и не зеленеют.
- Рубрика не требует выдумывать неизвестные характеристики или гарантию:
  честное, конкретное уточнение каждого условия допустимо. Это не отменяет
  проверку полноты примера. Невалидные ссылки оценщика не дают pass/fail даже
  при наличии других корректных ссылок в том же выводе.

Локальные регрессионные проверки без расходов на провайдера:
`npm test -- src/__tests__/reportRegression3bc.test.ts` и
`admin-frontend/src/widgets/audit-analytics-report/model/dialogExamples.test.ts`.
Моковый успех не сертифицирует все 29 пунктов: для проверки реальной модели

После повторного прогона `49bdf262-424a-4add-bf6b-fdb5bd0e669f` версия
оценщика отчётов — `report-2026-10-30.3`. Исправлены дополнительные причины:

- Локальный fallback теперь тоже проходит полный валидатор. Он сохраняет
  корректные факты исходной реплики, а не заменяет их общим вопросом. Если
  безопасный пример построить нельзя, он остаётся отсутствующим: критерий не
  зеленеет лишь из-за наличия шаблона. Вопросы вида «какая модель и что важно?»
  распознаются как два уточнения, даже с единственным знаком «?».
- У всех положительных реплик тоже нужен содержательный комментарий.
  Нормализатор использует подтверждённые действия менеджера; оставшиеся пробелы
  исправляет ограниченный дополнительный проход генерации. Чтение готового
  отчёта не инициирует AI-запросов. Сбой восстановления не создаёт выдуманную
  оценку и остаётся виден в проверке полноты.
- Сильные действия считаются отдельно от общей метки реплики. Правильная цена
  или представление не исчезают из strengths из-за другого недостатка.
  Противоречащая находке цитата не подтверждает успех по тому же действию.
- Темы слабых сторон определяются по заголовку, не случайному глаголу в
  комментарии. Сводка объединяет повторы презентации и фиксации визита, но
  сохраняет отдельные карточки разных ошибок и самостоятельный follow-up.
  Если менеджер уже назвал слот, используется вариант заголовка существующего
  кода NO_CONCRETE_NEXT_STEP «Не закрепил детали следующего шага»; это не новый
  критерий, не изменение балла и не правка справочника в БД.
- Год обслуживания раньше известного года автомобиля и явно конкурирующие
  ASR-варианты года сохраняются как `transcription_uncertainties`. Это эвристика
  необходимости прослушивания, **не исправление транскрипта и не доказательство
  сбоя ASR**. Флаг misinformation требует цитаты менеджера; спорная дата или
  общее «всё нормально» сами по себе не дают штраф. Независимо подтверждённые
  ошибки и приложение с fact_context.misinformation_detected не подавляются.
  Классификация, прямо понижающая пункт за отмеченный спорный ASR, требует
  повторной попытки, а не публикации заведомо неверного результата.
- Метаданные неопределённости передаются в обычный отчёт и показаны отдельно
  как «Нужно проверить запись». Они берутся из прикладного оценщика, а не из
  предложенной моделью отговорки. В примере нельзя выдавать спорный год за
  проверенный факт или выдумывать правильный год вместо него.
- Оценщик откалиброван: краткое summary не обязано повторять каждую находку;
  ответ про датчики не обязан повторять бюджет, если не противоречит ему.

После прогона `48dc0cca-d548-4f54-b5b7-6230031dda93` версия —
`report-2026-10-30.4`. Правки применены к общей генерации реальных отчётов
звонков и тренировок, а не только к оценщику автотестов:

- Замечания и рекомендации связаны по `problemCode`. Представление имени и
  компании не дублируется разными заголовками в weaknesses. Отсутствие
  повторного контакта после отправки документов отделено от общего пассивного
  стиля; предложенный, но не подтверждённый слот одинаково называется в
  находках и рекомендациях. Изменения справочника — только для генератора,
  существующие записи БД не переписываются.
- Категории сохраняют баллы рассчитанной оценки: важность текстовой находки
  больше не применяет второй скрытый штраф при сборке отчёта. Само приглашение
  на визит можно отметить как частичное действие, не как подтверждённую запись.
- После структурного валидатора каждый полный пример проходит отдельную
  смысловую проверку по ВСЕМ его находкам, прямому ответу, сохранению фактов и
  отсутствию выдумок. Нужны точный хеш кандидата и дословные свидетельства по
  каждому пункту; общий неподкреплённый `pass` не принимается.
- Пропуски имени/компании и условий «снег / дождь / грязь / гарантия»
  проверяются дополнительно локально. Содержательное исправление получает
  конкретные причины отклонения и проходит повторную проверку. Цикл ограничен
  одной дополнительной смысловой правкой (структурные попытки внутри — до 2).
  Неизменённый отклонённый текст не переоценивается в надежде получить pass.
- `report.exampleReviews` хранит статус, хеш, причины и отклонённые кандидаты.
  Отклонённый финальный пример скрыт, но причина доступна в обычном отчёте и
  архиве по ID. Чтение не генерирует новый шаблон поверх отказа и не вызывает
  API; изменённый текст не наследует прежнее подтверждение.
- Недоступная смысловая проверка даёт `review`, а не зелёный пункт. Проверки
  `report-all-problems` / `report-better-only` требуют подтверждения текущего
  кандидата; независимый оценщик остаётся дополнительным контролем. Ошибки
  доступа/баланса провайдера не маскируются смысловым успехом.

Локальные контрпримеры: `src/__tests__/reportRegression48.test.ts` и
`ExampleReviewNotice.test.tsx`. Они используют моки и не заменяют новый
оплачиваемый прогон реальной модели с базой `48dc0cca-d548-4f54-b5b7-6230031dda93`.
Старый архив остаётся неизменным.

После `b8bac984-c592-4e1f-b253-d9b8740ac09b` версия — `report-2026-11-01.1`.
В этом прогоне было 12 завершённых сценариев, но 9 fail / 15 review / 5 pass
на уровне общего чек-листа. Это не доказательство ухудшения самих диалогов:
часть прежних pass стала review из-за нового контроля, а часть отказов вызвала
некорректная рубрика проверяющего. Исправления:

- Генератор, редактор примеров и независимый проверяющий используют общий
  `REPORT_EXAMPLE_ACCEPTANCE_RULES`: неизвестное имя допускает `[имя]`,
  представление не требуется в каждой реплике, неизвестные технические свойства
  не нужно выдумывать, один вопрос о времени повторного контакта допустим.
  Это не отменяет проверки всех условий вопроса и сохранения исходных фактов.
- Отклонённые в архиве переписывания с подтверждённым бюджетом больше не
  блокируются из-за одного слова «бюджет», которое раньше встречалось в
  будущем сообщении клиента. Новые имена, суммы и содержательные потребности
  остаются под контролем валидатора.
- Проверка сохраняет и действия: отправку подтверждения, конкретную запись на
  осмотр. Структурное отклонение теперь записывает точную причину, а не общий
  перечень возможных проблем.
- В `exampleReviews.checks` и `validationIssues` сохраняются ответы оценщика и
  конкретные ошибки формата/цитат. Только невалидное заключение повторяется
  один раз; валидный fail или семантический review не переоценивается ради pass.
- Независимая проверка идёт группами до 6 критериев с короткими дословными
  подстроками `references[].quote` вместо копирования целых массивов и длинных
  примеров. Подстрока проверяется по указанному JSON Pointer. Старый точный
  `value` также поддержан; смешанные и выдуманные ссылки не принимаются.
  Обрезанный/неполный JSON повторяется один раз, сбой одной группы не стирает
  успешные группы, ошибки доступа/баланса и отмена по-прежнему останавливают
  выполнение.
- Сильная сторона «подтвердил наличие» больше не заменяется формулировкой
  «уточнил автомобиль». Повтор про отсутствие формата визита не добавляется,
  если этот же пробел уже описан в конкретной находке о следующем шаге.
- Уточнение критерия/приоритета относится к NO_NEEDS_DISCOVERY, а не к
  повторной NO_REQUEST_CLARIFICATION о том же вопросе. Ссылки рекомендаций
  переклассифицируются вместе с находкой; уточнение конкретной модели остаётся
  самостоятельным запросом. Самоотрицающая находка PRODUCT_MISINFORMATION с
  текстом «фактической ошибки нет» требует повторной генерации всего JSON с
  причиной отклонения. Она не публикуется и не удаляется молча.
- У штатного классификатора есть узкая проверка противоречивого
  `PRODUCT_PRESENTATION=NO`: если менеджер назвал известные модель, цену,
  наличие и содержательные условия, классификация перепроверяется, прежде чем
  рассчитывается балл. Это не автоматическое начисление баллов; при устойчивом
  противоречии оценка недоступна. Правило не применяется к пользовательским
  чек-листам, подтверждённой дезинформации или несовпадающей цене.

### Сравнение Luna с усиленным reasoning

Общая модель задаётся через `OPENAI_CHAT_MODEL` в `.env`, провайдер остаётся
`AI_API_PROVIDER=proxyapi`. Для оценки, генерации, ремонта и проверки отчётов
можно явно задать `OPENAI_REASONING_EFFORT=high` (`low` / `medium` / `high`).
Профиль `report-staged-v1` оставляет заданный режим для основной классификации
и полной генерации отчёта (включая повтор полной генерации). Дополнение
находок/аннотаций, исправление и проверка примеров, а также тестовый оценщик
используют максимум `medium`: при базовом `high` — `medium`, при `medium` или
`low` — тот же выбранный режим. Модель остаётся общей, отдельных настроек
модели или дополнительных переменных окружения для стадий нет.
Без переменной сохраняется режим провайдера; старым моделям вроде GPT-4o
параметр не отправляется. Телефонный Realtime этим параметром не меняется.
Базовый режим сохраняется в `configuration.reasoningEffort`, версия профиля —
в `configuration.reasoningProfileVersion`, фактические режимы стадий —
в `configuration.reasoningByStage`. Они влияют на хэш сравнения. Старые архивы
без профиля не переписываются: предыдущий прогон Luna high использовал high
во всех стадиях. Промпты, критерии и лимиты токенов при разделении не менялись.
После изменения `.env` нужен перезапуск серверного процесса.

Платный локальный перетест от имени владельца существующего архива:

```sh
node --import tsx scripts/retest-report.ts --reference <UUID> --execute
node --import tsx scripts/retest-report.ts --reference <UUID> --scenario trainer-strong --execute
```

Без явного `--execute` запросы не запускаются. Скрипт использует тот же
обработчик, сохраняет новый UUID/parentRunId и выводит прогресс и оценочную
стоимость. Это локальная административная команда, не HTTP-авторизация.

В расчёте стоимости reasoning уже входит в `completion_tokens` и не должен
оплачиваться повторно. Обычный тариф чтения кэша отделён от `272K+`;
обновление тарифов создаёт новый снимок исправленного парсера. Старые
архивы и исторические оценочные расходы автоматически не переписываются.

Локальный разбор без новых API-запросов:

```sh
npm run inspect-autotest -- <UUID> --check report-single-example --json
npm run inspect-autotest -- <UUID> --scenario trainer-closing --compare <previous-UUID>
```

Служебные поля владельца/процесса исключаются, ключи и токены редактируются.
Нужен доступ к архиву того сервера, где выполнялся тест; один UUID не даёт
доступа к чужой файловой системе. Сохраняйте `storage/report-regression` на
постоянном томе при деплое.

## Автотестирование тренировок

Адрес: `/testing?tab=autotesting&target=trainer`. Нажмите запуск всей серии
или выберите пункты. Предыдущие тренировки и ручной выбор профиля не нужны:
сценарий покупки автомобиля, легенды, вопросы и возражения встроены в
`src/testing/trainerBuiltinFixtures.ts`. Данные вымышленные, одинаковые для всех
компаний и не зависят от записей сотрудников. Код обработки и API-настройки
тренажёра остаются реальными, ответы AI и аудио не подменяются заглушками.
Проверяются 20 согласованных критериев в четырёх группах:
«Голос и подача», «Роль клиента», «Работа с ответами менеджера», «Ход тренировки».

Семь сценариев: обычный диалог; женский профиль/легенда; числа и бренды;
длинный ответ/несколько вопросов/смена данных; уход от темы/переспрос;
два исправляющих голосовых; полный сценарий и завершение. Можно запустить
всю серию, один сценарий или пункт — с тем же компактным отчётом, историей,
сравнением, JSON-экспортом и живыми обновлениями WebSocket/REST.

Профили выбираются автоматически: «Скептик» (Андрей), «Сомневающаяся» (Мария)
для женского сценария, «Болтун» (Олег) для длинного сообщения. Тон всех трёх
профилей оценивается по своим критериям. Легенда содержит автомобиль, бюджет,
срок покупки, способ оплаты, автомобиль на обмен, состав семьи и неизвестные
поля. Данные автомобиля совпадают и в контексте резервной модели.

Голос автоматически разрешается из включённого каталога по мужскому/женскому
пресету или явной отметке пола; выбор детерминирован. Если подходящей записи
нет, используются имеющиеся в тренажёре OpenAI-пресеты `onyx`/`nova`, а не
один общий мужской голос для обоих полов. Идентификаторы ElevenLabs зависят
от аккаунта и не зашиваются случайными значениями. Фактически выбранные
голоса входят в снимок/хеш настроек и проверяются по событиям TTS.

Тестовый адаптер вызывает те же `initializeTrainerDialog`,
`runTrainerSessionTurn`, STT, ElevenLabs Agent/резервную модель и TTS, что
обычная тренировка. `TrainerSimulationStore` заменяет только сохранение
сессии на память; для встроенного набора даже не ищется TrainerSession-образец.
Не создаются обычные TrainerSession, баллы, записи дневного
плана или отчёты сотрудника. API-расходы отмечаются как `trainer_autotest`.
Менеджерские фикстуры озвучиваются полностью отдельным TTS и проходят
реальный STT. Их WAV кешируются в `storage/trainer-regression/fixtures`;
ограничение длины TTS клиентских ответов к тестовому менеджеру не применяется.
Для встроенного набора менеджер получает отдельные подтверждённые факты
`managerFixture`: наличие, история, цена/доплаты и осмотр. Эти сведения не
попадают в легенду клиента. Ответы менеджера выбираются по реальному вопросу,
а не генерируются из неопределённой легенды с бесконечным «уточню».
Для старых пользовательских наборов адаптивный менеджер по-прежнему использует
`openaiChatModel`. Генерация проверяемого клиента, TTS/STT и смысловой оценщик
остаются реальными оплачиваемыми запросами.

Фиксируются фактические TTS-провайдер и voiceId каждого ответа, в том числе
переход на резервный голос. Изменение выбранного голоса, пустое аудио или
обрезание текста, переданного в TTS, дают `fail`. Пол на слух, тембр,
искажения, ударения и вопросительная интонация остаются `review` до
прослушивания записи. Текстовый оценщик обязан ссылаться на существующие
реплики AI; оценка менеджера вместо клиента или отсутствие свидетельств
не дают зелёного результата. Частичный запуск не подтверждает всё направление.

Пункт 17 отправляет **два отдельных** голосовых до готовности первого ответа.
После разбора `433b864f-7024-48fb-8ca7-afa75682d088` используется общий с
HTTP `TrainerVoiceTurns`: STT каждого сообщения выполняется отдельно, порядок
сохраняется по поступлению, тексты и исходные аудио объединяются в одну
логическую реплику менеджера. До атомарного начала сохранения ответа можно
прислать уточнение, в том числе пока модель или TTS ещё обрабатывают старую
версию. Устаревший результат не сохраняется и не отправляется пользователю;
контекст ElevenLabs сбрасывается и ответ формируется заново по полному вводу.
Один принятый логический ход — один ответ клиента. Ранние HTTP-запросы получают
`superseded=true`; браузер не воспроизводит их как дополнительные ответы.
Кнопка записи доступна во время ожидания для нового уточнения. После начала
сохранения ответ уже нельзя заменить: в узком окне до отправки возвращается
409, после доставленного ответа новое сообщение — следующий ход.
Лимиты: до восьми записей / 20 МБ на логический ход; окно сбора после STT 40 мс.
Сборка аудио исправления использует тот же FFmpeg и сохраняет оба исходных
голосовых в общей записи, не выдаёт последний клип за всю реплику.

Версия встроенных фикстур `2026-10-30.2`, оценщика `trainer-2026-10-30.3`.
Оценщику передаются явные `turnIndex` с нуля и `speaker=ai_client` /
`manager_fixture`; недостоверные ссылки не исправляются догадкой «минус один».
Ошибки входного ASR (например, Esteo → Steo в речи менеджера) не объявляются
доказанной ошибкой TTS клиента. Не проверенные на слух пункты остаются review.
Реальная обработка тренажёра прерывает повторное «Хорошо, жду» переходом к
нераскрытому вопросу сценария, а при завершении/лимите гарантирует прощание
до финальной озвучки и сохранения. Это не делает пропущенный сценарий успешным:
полноту вопросов/возражений по-прежнему отдельно проверяет оценщик.

Каждому запуску присваивается UUID; снимки и MP3 сценариев сохраняются отдельно
в `storage/trainer-regression/<ID>/`. В записи между репликами остаётся 300 мс.
Постоянная ссылка: `/testing?tab=autotesting&target=trainer&runId=<ID>`.
Нужны постоянный том/резервные копии **обоих** архивов. Диагностика автоматически
находит нужный архив по UUID:

```sh
npm run inspect-autotest -- <ID> --json
npm run inspect-autotest -- <ID> --check trainer-correction --json
```

У CLI `--compare` для тренировок выводит два сохранённых диагностических снимка;
табличное сравнение статусов и метрик доступно в интерфейсе.
REST: `/api/admin/auto-testing/trainer/runs` (start/history/get/compare/cancel/audio/live-ticket
по той же структуре, что call-plan). Новый запуск — `{checkIds? | scenarioIds?, referenceRunId?}`;
sourceId можно не передавать, либо указать `trainer-builtin-v1`.
В истории видны и старые запуски, отчёты по ID не мигрируются и не удаляются.
Архивная проверка по образцу открывается в режиме просмотра; для нового запуска
в интерфейсе нужно вернуться к встроенному набору. Старый API `sources` и
sourceId/femaleSourceId для прежних клиентов сохранён с прежней проверкой
доступа к исходным тренировкам. Веб-интерфейс больше не запрашивает этот список.
Старые и новые условия различаются хешем/версией оценщика и не дают ложного
вывода об исправлении при сравнении. Отчёты тестов ограничены владельцем.
WebSocket-билеты дополнительно привязаны к направлению, не могут использоваться
между call-plan и trainer. Чтение отчёта/истории/записи не запускает провайдеров.
Отмена прерывает агентское соединение и сохраняет результат после окончания
текущей операции; уже отправленный запрос TTS может завершиться не сразу.

При первой проверке выбирайте один пункт/сценарий: полная серия выполняет
десятки STT/генераций/TTS. Обычные unit/integration-тесты подменяют провайдеров
и не расходуют API-баланс. Подход к раздельным программным и модельным
проверкам описан в [OpenAI: Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices).

## Живые обновления

REST-коллекция: `/api/admin/auto-testing/call-plan/runs`:

- `POST /` — запуск, `{planId, checkIds? | scenarioIds?, referenceRunId?}`;
- `GET /?planId=...` — история;
- `GET /:runId` — текущий снимок;
- `GET /:runId/compare?against=...` — сравнение;
- `POST /:runId/cancel` — отмена;
- `GET /:runId/audio/:caseId` — WAV-запись;
- `POST /:runId/live-ticket` — короткоживущий одноразовый билет;
- `WS /:runId/live?ticket=...` — начальный снимок и события `run.snapshot`.

Запуск требует доступа к плану. История, записи, билет и WebSocket ограничены
владельцем запуска. В URL WebSocket не передаётся JWT аккаунта или ключ API.
Билет действует 45 секунд и используется один раз; есть heartbeat и ограничение
буфера медленного клиента. Ошибка наблюдателя не останавливает тест. Ключи
провайдеров остаются только на сервере.

Подготовка фикстур, подключение, текущие реплики, транскрипт, инструменты,
оценка и результаты публикуются по мере выполнения. При разрыве браузер
переподключается с новым билетом; резервный опрос REST работает раз в 3 секунды.
Vite проксирует `/api` с `ws: true`. Для production в
`nginx.prod.conf.example` добавлен отдельный location с Upgrade/Connection и
отключённым access-log для URL с билетом. Его нужно перенести в действующий
nginx-конфиг при деплое и перезагрузить nginx. Без Upgrade работает резервный
опрос; локальный конфиг системного nginx автоматически не изменяется.
Отмена/окончание/уход со страницы очищают браузерные таймеры и соединения.
Переоткрытие страницы восстанавливает последний запуск из истории.

## История и сравнение

Отчёт разделён на «Проверки», «Сценарии» и «Сравнение с прошлым тестом».
Сверху — четыре счётчика-фильтра: пройденные, ошибки, требующие проверки и
непроверенные пункты. Быстрый фильтр «Требуют внимания» объединяет только
ошибки и ручную проверку, но не считает незапущенные пункты ошибками.

Чеклист сгруппирован по четырём направлениям: начало/качество связи,
темп диалога, понимание/легенда, сценарий/завершение. Изначально раскрывается
только первая группа с ошибкой (или ручной проверкой), отдельные свидетельства
всегда свёрнуты. Внутри пункта доступны описание, выводы, связанные сценарии и
точечный перезапуск. Живые обновления не сбрасывают выбранный раздел и группы.
Будущие неизвестные критерии попадают в «Другие проверки», а не теряются.

В сценариях отдельно раскрываются критерии, диалог и функции; запись
загружается только по кнопке. История по умолчанию свёрнута. В сравнении
неизменившиеся строки скрыты до включения «Показать без изменений».

Старые отчёты и URL `/api/admin/realtime-test/regressions` сохранены.
Новые запуски помечены `target=call_plan`, `executionMode=simulation`; старые —
архивом гипотезы. Разные контуры/модели/снимки конфигурации/покрытие не дают
ложного вывода «исправлено». Повтор нового теста проверяет текущий план, а не
замороженный старый промпт. Случайный профиль может отличаться; это отмечается
предупреждением сравнения. Реальные обращения к OpenAI/ElevenLabs платные.

## Постоянный ID и разбор конкретного запуска

UUID создаётся до начала выполнения и атомарно сохраняется в
`storage/realtime-regression/<ID>/report.json`. Тот же ID отображается в отчёте
и истории; повторный тест получает новый ID с `parentRunId` исходного запуска.
Старые результаты не перезаписываются результатами повторного теста.
В раскрытом критерии и сценарии видны их стабильные ID (`ending`, `callback`
и т. п.), чтобы можно было указать конкретное место проблемы.

Кнопки «Копировать ID» и «Копировать ссылку» позволяют прислать запуск для
разбора. Постоянный адрес: `/testing?tab=autotesting&runId=<ID>`.
Поле «Открыть сохранённую проверку по ID» не зависит от первых 30 строк
истории. При обновлении страницы открывается именно указанный запуск,
а не последний. Даже если его план не входит в текущий фильтр компании,
доступен просмотр своего отчёта; новый запуск требует доступного плана.
Ссылка не является публичной: REST/WebSocket по-прежнему проверяют владельца.

Для диагностики в рабочем каталоге проекта:

```sh
npm run inspect-autotest -- <ID>
npm run inspect-autotest -- <ID> --check ending --json
npm run inspect-autotest -- <ID> --scenario callback --json
npm run inspect-autotest -- <новый-ID> --compare <предыдущий-ID> --json
```

Это **чтение локального архива**, без сервера, БД, подключения к провайдерам,
повторного запуска или изменения отчёта. В диагностике доступны свидетельства,
транскрипт с метриками реплик, события воспроизведения, функции, ошибки,
результаты оценщика и сохранённый промпт/настройки (в JSON). Владелец, произвольные
поля конфигурации и ключи авторизации не экспортируются; известные credential-поля
и Bearer/sk-секреты маскируются. Диалоги и промпты могут содержать персональные
данные — диагностический вывод не предназначен для публичного размещения.
Локальный загрузчик предназначен только для доверенной консоли с файловым
доступом и не используется HTTP-обработчиками.

Чтобы анализировать по одному ID тест, выполненный **на другом сервере**,
нужен доступ к его архиву. Если такого доступа у помощника нет, используйте
«Скачать отчёт» и приложите JSON. ID сам по себе не предоставляет удалённый
доступ. При деплое нужно сохранять каталог `storage/realtime-regression` на
постоянном томе/в резервных копиях; удаление этого каталога удалит архив.
