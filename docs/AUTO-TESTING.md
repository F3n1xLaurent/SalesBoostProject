# Автотестирование

`/testing` разделена на два таба:

- `Гипотезы` — прежние изолированные телефонные эксперименты;
- `Автотестирование` (`/testing?tab=autotesting`) — проверки без набора номера.

Направления задаются каталогом `GET /api/admin/auto-testing/catalog` со стабильными
ID `call_plan`, `report`, `trainer`. Реализованы `call_plan` и `trainer`;
`report` остаётся будущим направлением, без фиктивного запуска.

## Что именно проверяется

Новый запуск использует **текущую серверную** `OPENAI_REALTIME_MODEL`, актуальный
промпт выбранного плана, выбор профиля/предмета и голос как при обычном звонке.
Проверяются общие механизмы диалога, VAD, функций, TTS и воспроизведения по
эмулируемому протоколу Voximplant. `createCallPlanSimulation` использует ту же
фабрику production-сессии и preflight, включая повторные подключения, что
`prepareProductionOpenAiRealtimeCall`. Ни `StartScenarios`, ни `prepareCallPlanTelephony`
не вызываются: номера не набираются, записи звонков/расписания/обычные оценки
не создаются. Результаты хранятся отдельно в `storage/realtime-regression`.

Фикстуры отдельных сценариев могут задавать специальную легенду, например
женский род; это не меняет исходный план. Модель из вкладки «Гипотезы» не
используется. Если основная телефония переключена на `elevenlabs_agent`, запуск
блокируется с объяснением, вместо проверки другого движка под видом основного.

Это не проверка всей телефонии: реальная PSTN-сеть, буферы Voximplant,
автозапуск расписания и генерация обычного отчёта не сертифицируются эмуляцией.
Качество звука/ударения остаются `review` для прослушивания. Полный `pass`
требует полного покрытия релевантных сценариев; прерванные/непроверенные пункты
не становятся зелёными. Тренировки проверяются отдельным набором ниже;
автотесты обычных отчётов остаются будущим направлением.

## Автотестирование тренировок

Адрес: `/testing?tab=autotesting&target=trainer`. Нажмите запуск всей серии
или выберите пункты. Предыдущие тренировки и ручной выбор профиля не нужны:
сценарий покупки автомобиля, легенды, вопросы и возражения встроены в
`src/testing/trainerBuiltinFixtures.ts`. Данные вымышленные, одинаковые для всех
компаний и не зависят от записей сотрудников. Код обработки и API-настройки
тренажёра остаются реальными, ответы AI и аудио не подменяются заглушками.
Проверяются 20 согласованных критериев в четырёх группах:
«Голос и подача», «Роль клиента», «Работа с ответами менеджера», «Ход тренировки».

Семь сценариев: обычный диалог; женский профиль/легенда; числа и бренды;
длинный ответ/несколько вопросов/смена данных; уход от темы/переспрос;
два исправляющих голосовых; полный сценарий и завершение. Можно запустить
всю серию, один сценарий или пункт — с тем же компактным отчётом, историей,
сравнением, JSON-экспортом и живыми обновлениями WebSocket/REST.

Профили выбираются автоматически: «Скептик» (Андрей), «Сомневающаяся» (Мария)
для женского сценария, «Болтун» (Олег) для длинного сообщения. Тон всех трёх
профилей оценивается по своим критериям. Легенда содержит автомобиль, бюджет,
срок покупки, способ оплаты, автомобиль на обмен, состав семьи и неизвестные
поля. Данные автомобиля совпадают и в контексте резервной модели.

Голос автоматически разрешается из включённого каталога по мужскому/женскому
пресету или явной отметке пола; выбор детерминирован. Если подходящей записи
нет, используются имеющиеся в тренажёре OpenAI-пресеты `onyx`/`nova`, а не
один общий мужской голос для обоих полов. Идентификаторы ElevenLabs зависят
от аккаунта и не зашиваются случайными значениями. Фактически выбранные
голоса входят в снимок/хеш настроек и проверяются по событиям TTS.

Тестовый адаптер вызывает те же `initializeTrainerDialog`,
`runTrainerSessionTurn`, STT, ElevenLabs Agent/резервную модель и TTS, что
обычная тренировка. `TrainerSimulationStore` заменяет только сохранение
сессии на память; для встроенного набора даже не ищется TrainerSession-образец.
Не создаются обычные TrainerSession, баллы, записи дневного
плана или отчёты сотрудника. API-расходы отмечаются как `trainer_autotest`.
Менеджерские фикстуры озвучиваются полностью отдельным TTS и проходят
реальный STT. Их WAV кешируются в `storage/trainer-regression/fixtures`;
ограничение длины TTS клиентских ответов к тестовому менеджеру не применяется.
Адаптивные ответы тестового менеджера и смысловая оценка используют
настроенную `openaiChatModel`; это оплачиваемые запросы.

Фиксируются фактические TTS-провайдер и voiceId каждого ответа, в том числе
переход на резервный голос. Изменение выбранного голоса, пустое аудио или
обрезание текста, переданного в TTS, дают `fail`. Пол на слух, тембр,
искажения, ударения и вопросительная интонация остаются `review` до
прослушивания записи. Текстовый оценщик обязан ссылаться на существующие
реплики AI; оценка менеджера вместо клиента или отсутствие свидетельств
не дают зелёного результата. Частичный запуск не подтверждает всё направление.

Пункт 17 действительно отправляет **два отдельных** голосовых до готовности
первого ответа. Он использует общий с HTTP механизм допуска реплик, а не
склейку текста. Текущий тренажёр отклоняет второе сообщение с 409, поэтому
тест фиксирует `fail` с содержимым потерянного исправления. Это обнаруженная
особенность текущего поведения, не скрытый успешной фикстурой результат.
В этом изменении сама семантика приёма исправлений не исправляется.

Каждому запуску присваивается UUID; снимки и MP3 сценариев сохраняются отдельно
в `storage/trainer-regression/<ID>/`. В записи между репликами остаётся 300 мс.
Постоянная ссылка: `/testing?tab=autotesting&target=trainer&runId=<ID>`.
Нужны постоянный том/резервные копии **обоих** архивов. Диагностика автоматически
находит нужный архив по UUID:

```sh
npm run inspect-autotest -- <ID> --json
npm run inspect-autotest -- <ID> --check trainer-correction --json
```

У CLI `--compare` для тренировок выводит два сохранённых диагностических снимка;
табличное сравнение статусов и метрик доступно в интерфейсе.
REST: `/api/admin/auto-testing/trainer/runs` (start/history/get/compare/cancel/audio/live-ticket
по той же структуре, что call-plan). Новый запуск — `{checkIds? | scenarioIds?, referenceRunId?}`;
sourceId можно не передавать, либо указать `trainer-builtin-v1`.
В истории видны и старые запуски, отчёты по ID не мигрируются и не удаляются.
Архивная проверка по образцу открывается в режиме просмотра; для нового запуска
в интерфейсе нужно вернуться к встроенному набору. Старый API `sources` и
sourceId/femaleSourceId для прежних клиентов сохранён с прежней проверкой
доступа к исходным тренировкам. Веб-интерфейс больше не запрашивает этот список.
Старые и новые условия различаются хешем/версией оценщика и не дают ложного
вывода об исправлении при сравнении. Отчёты тестов ограничены владельцем.
WebSocket-билеты дополнительно привязаны к направлению, не могут использоваться
между call-plan и trainer. Чтение отчёта/истории/записи не запускает провайдеров.
Отмена прерывает агентское соединение и сохраняет результат после окончания
текущей операции; уже отправленный запрос TTS может завершиться не сразу.

При первой проверке выбирайте один пункт/сценарий: полная серия выполняет
десятки STT/генераций/TTS. Обычные unit/integration-тесты подменяют провайдеров
и не расходуют API-баланс. Подход к раздельным программным и модельным
проверкам описан в [OpenAI: Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices).

## Живые обновления

REST-коллекция: `/api/admin/auto-testing/call-plan/runs`:

- `POST /` — запуск, `{planId, checkIds? | scenarioIds?, referenceRunId?}`;
- `GET /?planId=...` — история;
- `GET /:runId` — текущий снимок;
- `GET /:runId/compare?against=...` — сравнение;
- `POST /:runId/cancel` — отмена;
- `GET /:runId/audio/:caseId` — WAV-запись;
- `POST /:runId/live-ticket` — короткоживущий одноразовый билет;
- `WS /:runId/live?ticket=...` — начальный снимок и события `run.snapshot`.

Запуск требует доступа к плану. История, записи, билет и WebSocket ограничены
владельцем запуска. В URL WebSocket не передаётся JWT аккаунта или ключ API.
Билет действует 45 секунд и используется один раз; есть heartbeat и ограничение
буфера медленного клиента. Ошибка наблюдателя не останавливает тест. Ключи
провайдеров остаются только на сервере.

Подготовка фикстур, подключение, текущие реплики, транскрипт, инструменты,
оценка и результаты публикуются по мере выполнения. При разрыве браузер
переподключается с новым билетом; резервный опрос REST работает раз в 3 секунды.
Vite проксирует `/api` с `ws: true`. Для production в
`nginx.prod.conf.example` добавлен отдельный location с Upgrade/Connection и
отключённым access-log для URL с билетом. Его нужно перенести в действующий
nginx-конфиг при деплое и перезагрузить nginx. Без Upgrade работает резервный
опрос; локальный конфиг системного nginx автоматически не изменяется.
Отмена/окончание/уход со страницы очищают браузерные таймеры и соединения.
Переоткрытие страницы восстанавливает последний запуск из истории.

## История и сравнение

Отчёт разделён на «Проверки», «Сценарии» и «Сравнение с прошлым тестом».
Сверху — четыре счётчика-фильтра: пройденные, ошибки, требующие проверки и
непроверенные пункты. Быстрый фильтр «Требуют внимания» объединяет только
ошибки и ручную проверку, но не считает незапущенные пункты ошибками.

Чеклист сгруппирован по четырём направлениям: начало/качество связи,
темп диалога, понимание/легенда, сценарий/завершение. Изначально раскрывается
только первая группа с ошибкой (или ручной проверкой), отдельные свидетельства
всегда свёрнуты. Внутри пункта доступны описание, выводы, связанные сценарии и
точечный перезапуск. Живые обновления не сбрасывают выбранный раздел и группы.
Будущие неизвестные критерии попадают в «Другие проверки», а не теряются.

В сценариях отдельно раскрываются критерии, диалог и функции; запись
загружается только по кнопке. История по умолчанию свёрнута. В сравнении
неизменившиеся строки скрыты до включения «Показать без изменений».

Старые отчёты и URL `/api/admin/realtime-test/regressions` сохранены.
Новые запуски помечены `target=call_plan`, `executionMode=simulation`; старые —
архивом гипотезы. Разные контуры/модели/снимки конфигурации/покрытие не дают
ложного вывода «исправлено». Повтор нового теста проверяет текущий план, а не
замороженный старый промпт. Случайный профиль может отличаться; это отмечается
предупреждением сравнения. Реальные обращения к OpenAI/ElevenLabs платные.

## Постоянный ID и разбор конкретного запуска

UUID создаётся до начала выполнения и атомарно сохраняется в
`storage/realtime-regression/<ID>/report.json`. Тот же ID отображается в отчёте
и истории; повторный тест получает новый ID с `parentRunId` исходного запуска.
Старые результаты не перезаписываются результатами повторного теста.
В раскрытом критерии и сценарии видны их стабильные ID (`ending`, `callback`
и т. п.), чтобы можно было указать конкретное место проблемы.

Кнопки «Копировать ID» и «Копировать ссылку» позволяют прислать запуск для
разбора. Постоянный адрес: `/testing?tab=autotesting&runId=<ID>`.
Поле «Открыть сохранённую проверку по ID» не зависит от первых 30 строк
истории. При обновлении страницы открывается именно указанный запуск,
а не последний. Даже если его план не входит в текущий фильтр компании,
доступен просмотр своего отчёта; новый запуск требует доступного плана.
Ссылка не является публичной: REST/WebSocket по-прежнему проверяют владельца.

Для диагностики в рабочем каталоге проекта:

```sh
npm run inspect-autotest -- <ID>
npm run inspect-autotest -- <ID> --check ending --json
npm run inspect-autotest -- <ID> --scenario callback --json
npm run inspect-autotest -- <новый-ID> --compare <предыдущий-ID> --json
```

Это **чтение локального архива**, без сервера, БД, подключения к провайдерам,
повторного запуска или изменения отчёта. В диагностике доступны свидетельства,
транскрипт с метриками реплик, события воспроизведения, функции, ошибки,
результаты оценщика и сохранённый промпт/настройки (в JSON). Владелец, произвольные
поля конфигурации и ключи авторизации не экспортируются; известные credential-поля
и Bearer/sk-секреты маскируются. Диалоги и промпты могут содержать персональные
данные — диагностический вывод не предназначен для публичного размещения.
Локальный загрузчик предназначен только для доверенной консоли с файловым
доступом и не используется HTTP-обработчиками.

Чтобы анализировать по одному ID тест, выполненный **на другом сервере**,
нужен доступ к его архиву. Если такого доступа у помощника нет, используйте
«Скачать отчёт» и приложите JSON. ID сам по себе не предоставляет удалённый
доступ. При деплое нужно сохранять каталог `storage/realtime-regression` на
постоянном томе/в резервных копиях; удаление этого каталога удалит архив.

## Проверки разработки

```sh
npm test -- src/__tests__/autoTestingLive.test.ts src/__tests__/autoTestingStart.test.ts src/__tests__/autoTestingNavigation.test.ts src/__tests__/hypothesis2ProductionParity.test.ts admin-frontend/src/shared/api/autoTesting.test.ts
npm test -- admin-frontend/src/pages/testing/ui/RegressionReport.test.tsx
npx tsc --noEmit
# Вне sandbox, если разрешено открытие loopback-порта:
RUN_LOCAL_WS_INTEGRATION=1 npm test -- src/__tests__/autoTestingWebSocket.integration.test.ts
```

Тесты используют подменённые провайдеры и не расходуют баланс API. Полную живую
серию пользователь запускает отдельно кнопкой на странице.
