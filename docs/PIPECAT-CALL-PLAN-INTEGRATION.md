# Pipecat как основной движок звонков по плану

Подключение выполнено 17 ноября 2026 года. Рабочая настройка backend: `CALL_PLAN_TELEPHONY_PROVIDER=pipecat`. `/health` возвращает `callPlanTelephonyProvider: "pipecat"`.

## Профиль

Профиль фиксируется сервером для каждого рабочего запуска: OpenAI `gpt-realtime-2.1`, ElevenLabs `eleven_v4_turbo`, смысловой контроллер, reasoning `low`, backchannel включён, trim idle audio выключен. Собственный TTS Realtime отключён. Голос и потребность берутся из профиля и сценария конкретного плана. Настройки экспериментальной формы `/testing` не меняют рабочий профиль.

Планы с явными обязательными вопросами используют свой список. Для сценариев без списка вопросов перед набором готовятся 2–4 темы из потребности и возражений сценария. Они сохраняются только в состоянии конкретного звонка, не меняют исходный план и его критерии оценки. Это нужно существующим планам, описанным через ситуацию клиента. На момент подключения вопросы заданных списков укладываются в ограничение контроллера 1–12.

## Запуск и очередь

Кнопка «Позвонить по аудитории» создаёт постоянные задания в `CallPlanCall`. Интерфейс показывает количество добавленных в очередь номеров. Обработчик запускается сразу после постановки в очередь, затем проверяет свободные задания раз в пять секунд. Расписание использует тот же обработчик и движок.

Каждый запуск проходит две стадии:

1. Backend проверяет доступ и подписку, выбирает профиль/голос, запрашивает подготовку Pipecat без набора номера. UUID заранее назначается backend.
2. После подготовки backend атомарно сохраняет `VoiceCallSession` и связь с заданием плана, затем вызывает `/production/sessions/{id}/start` с тем же UUID.

Рабочий `callId` равен UUID Pipecat, диагностический ID — `pc-<callId>`. Контекст содержит профиль движка и ссылку на диагностику. Повторный запрос start не выполняет второй `StartScenarios`. При потерянном ответе запуска не используется другой движок и не повторяется набор: состояние выясняет обработчик восстановления.

Текущая общая ёмкость сервиса — четыре подготовленных/активных сессии. При заполнении задания возвращаются в очередь. Доступ к плану, актуальность номера, состав аудитории и подписка перепроверяются перед реальным запуском. Ручные задания работают также у планов без включённого автоматического расписания.

## Результат и восстановление

Рабочий сценарий Voximplant `voice_pipecat`, правило `voice_pipecat_rule`. Он запускает стереозапись при соединении и передаёт её фактический статус, ID сессии Voximplant и события Pipecat. Старые правила `voice_openai_realtime` и экспериментальное `voice_pipecat_hypothesis` не перезаписывались.

Backend опрашивает приватный рабочий API раз в две секунды. Опрос сохраняет снимки в `storage/voice-pipecat` и контекст звонка, отмечает соединение, а после завершения медиапайплайна передаёт результат в существующий обработчик звонков. Далее используются прежние скачивание записи, повторная транскрибация, оценка чеклиста/сценария, отчёт, привязка к менеджеру/дилеру и отражение в истории плана. Повторная доставка результата не должна создавать вторую платную оценку.

Начальный текст клиента берётся из реально подтверждённых телефонным воспроизведением ответов. Неозвученная генерация не выдаётся за сказанное. Стереозапись и её повторная транскрибация остаются источником для разбора прерываний и неполных реплик.

После рестарта backend обработчик находит незавершённые рабочие звонки в базе и продолжает обработку их UUID. Он никогда не инициирует новый набор. Неиспользованная подготовка отменяется; потерянные до старта задания с временными ID возвращаются в очередь только в ограниченном окне восстановления. Если сам процесс Pipecat перезапущен, его активный разговор не возобновляется: сохранённый результат помечается как прерванный/ошибочный и обрабатывается без повторного звонка.

Публичный legacy webhook не принимает события рабочих Pipecat-звонков. Их результаты поступают через авторизованный приватный API. Рабочие записи исключены из общего экспериментального журнала `/testing`, чтобы не раскрывать их через доступ к тестовому стенду.

## Эксплуатация

Локально backend работает на хосте, Pipecat — в Docker. Для перечитывания `.env` и обновления Python-сервиса:

```sh
npm run pipecat:up
```

Рабочий сценарий Voximplant:

```sh
npm run pipecat:deploy-production
```

Для размещения обоих сервисов в Docker предусмотрен overlay:

```sh
docker compose -f compose.prod.yaml -f compose.pipecat.prod.yaml up -d --build app pipecat
```

На сервере необходимо задать постоянный публичный HTTPS/WSS адрес Pipecat через backend (`PIPECAT_HYPOTHESIS_PUBLIC_URL`, обычно `https://<домен>/pipecat`) и общий токен. Приватный API контейнера не публикуется наружу. Сохранять нужно volumes Pipecat и `storage` backend. Перенос текущей локальной установки на отдельный сервер в эту работу не входил.

Production overlay монтирует отдельный `salesboost_voice_pipecat` в `/app/storage/voice-pipecat`; образ создаёт каталог с владельцем node и правами 700. Без volume запись снимка в read-only контейнере не работает. Настройка окружения и шаги выкладки: [PIPECAT-PRODUCTION-SETUP.md](PIPECAT-PRODUCTION-SETUP.md).

Откат новых звонков: задать `CALL_PLAN_TELEPHONY_PROVIDER=openai_realtime` и перезапустить backend. Существующие незавершённые Pipecat-звонки продолжает обрабатывать worker независимо от выбранного движка новых звонков.

## Проверки и границы

- Сборка backend/frontend и TypeScript-проверка прошли.
- 126 backend-тестов прошли: выбор движка, двухфазный запуск, потеря ответа start, восстановление заданий, сохранение записи/расшифровки, оценка и зеркалирование отчёта в план, защита от повторной оценки, прежний движок и экспериментальный gateway.
- 393 Python-теста прошли в Docker, включая идемпотентный старт, сохранение состояния, отсутствие набора при подготовке/восстановлении, ёмкость, приватность рабочих журналов и подготовку сценария без списка вопросов.
- На реальных API проверена подготовка рабочего профиля. После успешной подготовки сессия отменена; endpoint start не вызывался, телефонных звонков и рабочих записей в статистике не создавалось.
- На реальных API отдельно проверен сценарий без явного списка: из опасения длительного оформления подготовились вопросы о сроке оформления и подготовке документов до визита. Эта сессия также отменена до набора.
- Сценарий и правило Voximplant загружены и проверены; здоровье Docker и выбранный движок backend проверены.

Первый реальный звонок по плану нужен для проверки записи и отчёта на живой линии. Полная цепочка обработки результата до отчёта проверялась с имитациями поставщиков и хранилища. Денежная стоимость прямых запросов OpenAI/ElevenLabs здесь не рассчитывается: исходные usage/метрики сохраняются, синхронизация расходов Voximplant идёт через существующую экономику. Старый стенд автоматических диалоговых проверок прямого Realtime не выдаётся за тест Pipecat и недоступен для нового основного движка; экспериментальные проверки Pipecat сохранены отдельно.

В semantic-12 добавлены шлюз линии, молчаливое завершение на автоответчике, ожидание/перевод и защищённый DTMF в обоих Vox-сценариях. IVR-события сохраняются в рабочей истории. Поведение и границы проверки: [PIPECAT-LINE-GATE.md](PIPECAT-LINE-GATE.md).
