# Диагностика медленных административных запросов

Целевые пути: `/api/support/meta` и `/api/admin/*`, включая проверку авторизации.
Замеры начинаются при входе в Express, до JSON-парсера и авторизации. Каждый
ответ получает `X-Request-ID` и `Server-Timing`. Медленные запросы, ответы 5xx
и оборванные подключения дают одну JSON-запись `[http-diagnostics]` в stdout.
Новая диагностика не записывает данные в БД и не делает внешних запросов.

## Настройка

```dotenv
HTTP_DIAGNOSTICS_ENABLED=true
HTTP_DIAGNOSTICS_SLOW_MS=1000
```

Это значения по умолчанию: достаточно выкатить код и перезапустить приложение.
`HTTP_DIAGNOSTICS_ENABLED=false` отключает сбор. Порог `0` временно включает
логирование всех целевых запросов. После диагностики верните 1000, чтобы не
увеличивать объём логов. Отдельная миграция БД для HTTP-диагностики не нужна.
Миграция очереди аналитики, если она выкатывается вместе с этим изменением,
по-прежнему обязательна.

## Как получить замер на проде

1. Открыть DevTools → Network и повторить медленное действие в авторизованной
   админке. Выбрать именно медленный запрос, например `/api/support/meta`.
2. В Response Headers посмотреть `Server-Timing` и `X-Request-ID`. В Timing
   посмотреть Queueing/Stalled и ожидание ответа сервера.
3. На сервере получить соответствующую запись по request ID:

```sh
docker compose -f compose.prod.yaml logs --since 10m app | rg '\[http-diagnostics\]'
docker compose -f compose.prod.yaml logs --since 10m app | rg -F 'ID_ИЗ_X_REQUEST_ID'
```

Можно использовать `grep`, если на сервере нет `rg`. Для сравнения полезны замеры
при отсутствии массовых звонков и во время нагрузки. Один быстрый ответ без
авторизации (401) не измеряет работу целевого обработчика.

## Значение полей

| Поле / этап | Что измеряется |
| --- | --- |
| `app` в Server-Timing | Время от входа в Express до отправки заголовков |
| `headersMs` в логе | То же время; null, если клиент отключился до заголовков |
| `durationMs` | Время до `finish` ответа на стороне Node или до закрытия соединения |
| `auth` | Проверка токена и загрузка аккаунта с memberships/templates |
| `dbMs`, `dbCount` | Суммарная длительность и число завершённых операций Prisma |
| `dbTop` | До пяти самых долгих групп model/action, с count/ms/maxMs |
| `support_categories` | Ожидание категорий поддержки, включая работу кеша и Bitrix24 |
| `bitrix_http` | HTTP-вызов Bitrix24 вместе с чтением JSON-ответа |
| `bitrix_refresh` | Обновление OAuth-токена Bitrix24, если понадобилось |
| `dbInFlight`, `pendingStages` | Незавершённые операции/этапы в момент окончания HTTP-запроса |
| `processCpuMs`, `eventLoopUtilization` | CPU всего процесса и загрузка его event loop за интервал запроса |

Этапы **пересекаются**: auth включает свою операцию Prisma, support_categories
включает Bitrix24, а параллельные операции могут суммарно длиться дольше запроса.
Складывать эти времена как последовательные части нельзя. `dbCount` — операции
Prisma, а не число SQL-запросов, выполненных движком при include/relations.
`dbMs` включает ожидание соединения/движка, SQL и получение результата; отдельно
время ожидания блокировки SQLite этот замер не выделяет. Метрики CPU/event loop
относятся ко всему процессу при параллельной нагрузке, а не только к этой ручке.

После HTTP-ответа сбор в его контексте прекращается. Фоновая аналитика не
продолжает изменять готовую запись. В уже начатом фоновом запросе, завершившемся
до HTTP-ответа, Prisma-операции могут попасть в тот же контекст.

## Как читать результат

- Большие `auth` и `Account.findUnique` в `dbTop` — основная задержка при загрузке
  аккаунта. Проверить нагрузку на БД, очередь соединения и запросы авторизации.
- Большие `support_categories` и `bitrix_http` — запрос ждёт справочник Bitrix24.
  Большой `bitrix_refresh` отдельно укажет на обновление токена.
- Большой `dbMs`, но короткий auth — смотреть операции самого обработчика в dbTop.
- Высокая загрузка event loop и CPU при небольших временах БД/Bitrix24 — повод
  проверить синхронную работу и общую нагрузку процесса.
- В браузере 4–5 секунд, а `app` и серверный `durationMs` малы — задержка вне
  измеряемого обработчика: очередь браузера, сеть, TLS или reverse proxy.
- `status: 499` — диагностическое обозначение оборванного подключения, а не код,
  отправленный приложением клиенту. Незавершённый auth с `dbInFlight: 1` покажет,
  что клиент отключился, пока бэкенд ещё ждал операцию БД.

Если нужно разделить задержку reverse proxy и бэкенда, в Nginx можно отдельно
сопоставить `$request_time`, `$upstream_connect_time`, `$upstream_header_time`,
`$upstream_response_time` и `$upstream_http_x_request_id`. Не используйте полный
`$request`/query string для такого диагностического лога.

## Что уже видно из кода

`/api/support/meta` ждёт `getBitrixSupportCategories()`. При холодном кеше либо
необходимости обновить OAuth-токен там возможен внешний запрос, поэтому ручка
не является только локальной выдачей констант. Все защищённые административные
ручки сначала загружают аккаунт из Prisma. В текущей конфигурации SQLite
используется `connection_limit=1`.

Это возможные места задержки, **а не подтверждённая причина продовых 4–5 секунд**.
Для вывода нужны реальные замеры новой версии под нагрузкой. Диагностику на
прод в рамках изменения не выкатывали.

Логи содержат только шаблон маршрута и технические тайминги. Полный URL,
query string, SQL/параметры, Bearer-токен, cookie, тела/результаты запросов и
идентификаторы пользователей не сохраняются. Неизвестный маршрут записывается
как `:unmatched`, а не как исходный путь.
