# Разбор pc-ad66f7f4-b748-46e8-8593-a788f23de15d

Версия звонка: `pipecat-stability-1`, `gpt-realtime-2.1` + `eleven_v4_turbo`. 1068 событий, девять реплик собеседника. Источник — приватный локальный экспорт в `storage/pipecat-diagnostics/`; содержимое звонка повторно внешним API не отправлялось.

## Что подтвердилось

- Ошибок API, pipeline и инструментов в этом журнале нет. Подготовка рабочего соединения ElevenLabs заняла 2263,58 мс до набора; в разговоре использован тот же сокет. OpenAI подключился с первой попытки. Первый ответ не запускался до обращения человека.
- На реплике «Вас это устроит?» завершённая генерация ещё воспроизводилась. Решение о перебивании принято на T+85,238 с, очистка очереди зарегистрирована на T+85,252 с, примерно через 14 мс после решения. Прерванный assistant item удалён до `req-7` (702 → 706). В следующем запросе оставались вопрос о скидке, ответ сотрудника и новая реплика; непрозвучавший вопрос о сроке владения не оставался обычной целой репликой assistant.
- Агент ответил на новый вопрос по существу и затем вернулся к сроку владения. Позднее «около года» было связано с этим вопросом: агент ответил «Понял, около года». Наблюдаемой потери контекста здесь нет.
- Длинное ожидание ответа этим звонком не проверено: максимальная пауза от предыдущего телефонного ACK до начала новой речи без наложения — около 1,16 с. Коротких «угу/ага» для проверки подавления перебиваний в расшифровке нет.
- Отбой запрошен на T+129,002 с, сразу после ACK последнего аудио на T+129,001 с. Разница до финального события отключения не равна задержке фактического отбоя: lifecycle callback и остановка транспорта приходят отдельно.

## Найденный дефект финала

На обычное подтверждение «Конечно, да, всё верно» модель сгенерировала завершающую фразу, которая уже пошла в TTS:

1. T+118,015 с — первый текст модели.
2. T+118,239 с — создан её TTS-контекст.
3. T+118,537 с — вызван `prepare_end_call(reason=conversation_complete)`.
4. T+118,548 с — транспорт создал ещё одно прощание.

Эвристика возможного завершения не распознала обычное подтверждение как closing candidate. Первый ответ не удерживался, поэтому подготовленная транспортом фраза дополнила уже начатый финал. Это дублирование, а не цикл ошибок `end_call`, который был в предыдущем звонке.

Одновременно новый глобальный response ID появился до окончания старого TTS-контекста. Поэтому общая отметка `tts_requested` была перезаписана, и старое аудио получило формально «92,84 мс», а следующий контекст — «3224,71 мс». Эти числа не позволяют сравнить чистую скорость двух синтезов. 10,15 с в финале — время от исходной речи до старта второго фрагмента, не задержка первого ответа.

## Исправление stability-2

Если завершающий текст уже выпущен моделью в TTS, `prepare_end_call` использует этот же response ID и ждёт его окончания. Второе транспортное прощание не добавляется. Если текст удержан либо не генерировался, остаётся одна подготовленная транспортом фраза. Уже выданный текст не обрывается ради замены: это создало бы слышимое заикание. Качество самой модельной фразы остаётся предметом проверки.

Добавлено событие `closing_existing_response_selected`. Метрика `response_tts_first_audio_ms` теперь связывает первый текст с первым аудио по response ID через TTS context ID. Она не использует общий таймер соседнего ответа; в сводке заменяет неоднозначную legacy-метрику TTS. Контекстные start/stop события также используют привязанный ID.

Регрессии проверяют обе ветки завершения и случай, когда первый звук старого контекста приходит уже после генерации нового ответа. Всего проходят 54 Python-теста. Production-пайплайн, модели и пороги VAD не менялись.

## Скорость

Для первых восьми ответов, до дублированного финала:

| Измерение | Медиана | Максимум | Образцов |
| --- | ---: | ---: | ---: |
| Конец речи → старт воспроизведения | 2622,51 мс | 3535,88 мс | 8 |
| response.create → первый текст | 1413,32 мс | 1988,33 мс | 8 |
| Первый текст → первое аудио TTS | 613,60 мс | 731,13 мс | 8 |

Определение конца реплики по всему звонку: медиана 257,69 мс; передача аудио → Voximplant started ACK: около 297 мс. STT — около 1048 мс, но работает параллельно с генерацией Realtime: прибавлять её к остальным стадиям нельзя. Наибольший измеренный участок — запрос → первый текст, включая сеть, очередь провайдера и генерацию; внутренние составляющие отдельно не измерены.

В случае короткого содержательного перебивания остановка ждала финальной STT: от акустического конца речи до решения прошло около 876 мс. Быстра сама очистка после решения, не весь путь распознавания намерения. Это цена текущей защиты коротких подтверждений; менять её без тестов «угу» и полноценного перебивания нельзя.

Цель ≤1,5 с пока не достигнута. По этому звонку скорость не улучшилась; сравнение с прошлым звонком не является контролируемым A/B-экспериментом. Следующий этап ускорения нужно направить на провайдерный участок LLM и агрегацию/синтез, сохраняя текущую границу VAD как измеряемый контроль. Большой прирост только от уменьшения примерно 258 мс endpointing невозможен.
