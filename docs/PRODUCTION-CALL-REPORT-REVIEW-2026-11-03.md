# Проверка отчётов прод-звонков 3 ноября 2026

Повторно загружены через диагностический API `app.salsa-sales.ru` звонки
895, 892, 880, 877, 874, 870, 867, 864. Выгрузки, транскрипции и локальные
результаты находятся в приватном временном каталоге, вне репозитория.
Изменение сохранённых отчётов, оценок и статистики в проде не выполнялось.

## Формула и категории

Для всех восьми звонков общий балл точно воспроизводится из сохранённого
чек-листа: YES = 1, PARTIAL = 0,5, NO = 0; NA исключается из знаменателя.
Формула: `round(100 × сумма(вес × выполнение) / сумма применимых весов)`.
В этих восьми сохранённых чек-листах все пункты имеют применимый статус,
сумма весов равна 100. Используется JS-округление; 37,5 → 38, 66,5 → 67.

| callId | Сохранённый общий балл | Повторный расчёт |
| --- | ---: | ---: |
| 895 | 30 | 30 |
| 892 | 38 | 38 |
| 880 | 74 | 74 |
| 877 | 58 | 58 |
| 874 | 73 | 73 |
| 870 | 67 | 67 |
| 867 | 59 | 59 |
| 864 | 70 | 70 |

Это подтверждает арифметику сохранённых классификаций, а не правильность
каждой классификации. Общий балл не равен простому среднему категорий.
Категории также округлены; вычисление из уже округлённых шкал может отличаться
от расчёта по исходным весам.

Подтверждены две ошибки отображения:

- Для кастомного чек-листа отсутствующую шкалу «Диагностика» заменяли общим
  баллом, а «Продукт» смешивал диагностику, презентацию и аргументацию.
  Теперь пять блоков рассчитываются непосредственно по категориям и весам
  сохранённых определений чек-листа, с исключением NA.
- Находка WEAK_OBJECTION_HANDLING относилась к «Закрытию», хотя её балл
  учитывался в продукте/аргументации. Категория унифицирована и для старых
  записей справочника. Дополнительный штраф при сборке отчёта не вводился.

Например, в 870 реальные веса блоков: контакт 14, диагностика 15,
продукт/аргументация 36, закрытие 23, коммуникация 12. Набрано соответственно
8, 8, 18, 23, 9,5 балла: всего 66,5 → 67. Слабая отработка сомнения в платеже
относится к продукту, а не снижает автоматически категорию записи на визит.

## Исправления качества

1. Общая шкала для оценщика, генератора и ремонта: positive — обязательный
   смысл выполнен; normal — полезный ответ с конкретным пробелом; negative —
   подтверждённая существенная ошибка/полный уход от вопроса. Оценка не требует
   буквального совпадения с эталоном или фамилии вместо запрошенного имени.
   Смешанный ответ может получить normal при одном подтверждённом действии.
2. Невалидные/отсутствующие примеры ремонтируются с конкретными причинами
   предыдущего отклонения; изменённый кандидат проверяется заново. Один и тот
   же отвергнутый текст не перегоняется через проверку до случайного pass.
   Готовый новый отчёт без примера для normal/negative не публикуется.
3. Находки связываются по исходной реплике и устойчивому коду, а не только
   заголовку. Дедупликация выполняется до лимита находок. Кастомные ID
   связываются с критериями при сверке сильных и слабых сторон; повторные
   перефразированные сильные стороны объединяются.
4. Информационный вопрос/просьба отделены от возражения и сообщения. Для
   возражения модель может дать точную цитату-триггер. Разночтения STT теперь
   учитывают не только годы, но и локальные изменения слов, например марки.
   Независимые доказанные нарушения не удаляются вместе со спорным словом.
5. Повторный запрос уже сообщённого имени не считается достижением; уточнение
   из-за явно плохой слышимости остаётся допустимым. «Не применимо» исключено
   из замечаний. Условие применимости в самой инструкции чек-листа учитывается
   даже при старом флаге allowNa=false; безусловно обязательные пункты по-прежнему
   нельзя самовольно исключить.
6. Идеальная фиксация даты/времени проверяется до расчёта оценки: диапазон,
   предложение без принятия другой стороной, отмена и расхождение часов не
   считаются подтверждённой записью. При противоречии оценщик получает запрос
   пересмотреть классификацию, вместо скрытого ограничения готового балла.

Дополнительно исправлена привязка цитат: длинная реплика с «Алло» больше не
приписывается короткому начальному «Алло». Комментарий с встроенным старым
«Можно лучше: …» не превращается в источник неподтверждённых характеристик.

## Проверка моделью и её ограничения

Пользователь отдельно разрешил передачу восьми транскрипций и сценариев
в настроенный сервис `openai.api.proxyapi.ru`, с маскированием телефонов.
Для проверки генерации сохранены исходные рассчитанные оценки; это не
пересчёт исторических баллов в проде.

- **874:** локально сгенерирован полный отчёт, все четыре проверяемые
  улучшенные реплики получили pass, пропущенных примеров нет.
- **892:** локально сгенерирован отчёт без пропущенных примеров; три проверки
  pass, одна review. По review обнаружено смешение исходной реплики и уже
  исправленного примера; инструкции проверяющего уточнены. Это review нельзя
  выдавать за независимое подтверждение корректности всех примеров.
- **864:** первый полный прогон выявил непрошедший пример завершающей реплики;
  публикация неполного результата остановлена. Дополнительная проверка старого
  отчёта выявила ложный «факт из будущего» для слова «чтобы», смешение исходной
  ошибки с исправлением и требование неизвестных размеров/функций. Добавлены
  исправления и регрессии, включая запрет реальной утечки сведений о детях
  из будущего контекста.
- **880, 895, 877, 870, 867:** проверка через модель остановлена HTTP 402.
  Повторная проверка исправленных примеров 864 также прервана HTTP 402.
  Дальнейшие модельные запросы не запускались. HTTP 402 теперь немедленно
  прерывает ремонт, без последующих попыток и подстановки результата как готового.

Полный живой прогон окончательного варианта для всех восьми случаев остаётся
неподтверждённым до восстановления доступа провайдера. Локальные регрессии
проверяют правила, привязку, скоринг и обработку ошибок с подменённой моделью;
они не гарантируют отсутствие любых смысловых ошибок живой модели.

Итоговые локальные проверки: 191 тест в 15 файлах прошёл; `npm run build`
и `git diff --check` завершились успешно. Пороговые правила не подкручивают
сохранённые баллы этих восьми звонков и не требуют дополнительных запросов
модели при чтении старого отчёта.
