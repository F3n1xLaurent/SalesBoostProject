# Dialogue State Manager: отдельный скоростной эксперимент

13 ноября 2026. Модель `gpt-realtime-2.1-mini`, reasoning `low`, текстовый Realtime WebSocket. Работающая гипотеза и production не изменялись. Звонков, STT, TTS, выполнения инструментов и записей CRM не было.

## Метод

План «Демонстрационный план прозвона» прочитан из локальной БД, скрипт «Скрипт для демонстрации», пять обязательных вопросов и три возражения. Использован настоящий генератор `buildRealtimeCallPrompt`. Профиль фиксирован на первом профиле скрипта, возраст фиксирован; автомобиль и компания вымышленные. Телефоны, цели плана и архивы звонков не читались. Снимок — `storage/pipecat-benchmarks/dsm/fixture.json` (ignored, mode 600).

**Fixed:** полный промпт генератора + действующий Pipecat legacy adapter. **DSM:** короткая постоянная роль, факты/профиль и одна инструкция `NEXT_TURN`, выбранная локальной машиной состояний после последней реплики менеджера. В модель не передаётся будущий план вопросов. Обоим доступны одинаковые три схемы существующих инструментов, `CALL_STATE` и одинаковая история.

Это конкретный локальный FSM для демонстрационного плана, с правилами распознавания ответов про наличие, пробег, пороги, ДТП, скидку, срок владения, запаску и обсуждение по телефону. Он не является универсальным смысловым классификатором. На произвольные ответы менеджера, отказы, несколько ответов сразу, исправления и неожиданные переходы эти замеры не распространяются. Дополнительного LLM-запроса на выбор состояния нет; его стоимость этим экспериментом не измерена.

Пять проходов на вариант, порядок fixed→DSM / DSM→fixed чередуется. В каждом десять ходов: начало, пробег, пороги, ДТП, скидка, срок владения, запаска, обсуждение по телефону, приглашение на осмотр, согласование времени. Итого 100 запросов в основном замере, плюс отдельный предварительный проход совместимости, который в итог не включён.

Для чистого сравнения применяется teacher forcing: после каждого запроса в следующую историю подставляется один и тот же контрольный ответ клиента. Сгенерированные ответы сохраняются для просмотра, но не меняют следующий вход. Это исключает расхождение историй как причину ускорения, однако не проверяет самостоятельный многоходовый диалог. Ответы создаются через `conversation: none` с одинаковым накопленным входом на каждый парный ход. Сокет и постоянная сессия открываются заранее; их установление не входит в таймер.

Отсчёт — до локального обновления состояния и подготовки запроса. Метрики: первое текстовое событие, первое законченное предложение после действующего SpeechFilter, конец генерации; отдельно локальная подготовка, токены и cache hits. Первое предложение может быть короткой реакцией «Понял»; это ещё не время до содержательного вопроса. Заключительный ход с инструментом исключён из обычных текстовых медиан и сохранён отдельно. Инструменты не исполняются, поэтому завершение/сохранение визита не считается проверенным.

Механизм управления контекстом сверялся с [официальной документацией OpenAI Realtime](https://developers.openai.com/api/docs/guides/realtime-conversations). Сокращение промпта само по себе не гарантирует ускорение: фиксированная часть может [использовать кэш](https://developers.openai.com/api/docs/guides/prompt-caching).

## Результат пяти проходов

Отчёт `dsm-922bc5b8-f571-4193-b79c-9e4f24f2b486`. Все 100 запросов завершены, ошибок API нет; подтверждены reasoning low, одинаковые три схемы инструментов и совпадение SHA256 истории на каждом парном ходе всех повторов. ## Что это означает для гипотезы

Локальное управление состоянием почти не добавляет задержки, а короткая задача на ход в этом тесте дала выигрыш порядка одной десятой секунды на LLM-этапе. Это разумный кандидат для последующего изучения контроля диалога. Одного перехода на DSM недостаточно, чтобы резко сократить всю паузу: распознавание, turn detection, TTS и доставка аудио здесь не измерялись.

Универсальный DSM с отдельным LLM-классификатором потребует дополнительного запроса. Его задержку нельзя считать равной измеренным 0.24 мс; выигрыш может исчезнуть. Здесь проверен конкретно локальный выбор состояния и одна генерация Mini.

Качество не подтверждено. В сырых ответах Fixed встречались пропуски тем и бессодержательное начало, у DSM — озвучка инструкции («Назови, пожалуйста…») и английское слово в русской фразе. На заключительных ходах оба варианта генерировали текст вместе с инструментом; DSM также иногда выдавал несколько вызовов. Это ответы модели до полного live-ограничителя закрытия, а не доказательство, что весь такой текст был бы озвучен текущей гипотезой. Исполнение, проверка фактов и playback ACK не запускались. Быстрый ответ нельзя автоматически считать корректным или естественным.

Промпт рабочей гипотезы сохранён. Для перехода нужен отдельный поведенческий эксперимент на неожиданном ответе, паузе, исправлении, перебивании и нескольких темах сразу, с существующими защитами инструментов и завершения.

Артефакт: `storage/pipecat-benchmarks/dsm/dsm-922bc5b8-f571-4193-b79c-9e4f24f2b486.json`. Предварительная проба `dsm-3effd070-d2f7-4665-ac76-1409fd254f5a` не включена в эти результаты. Проверки синтаксиса Python, генерации fixture TypeScript и `git diff --check` прошли. Production-код не менялся.

## Воспроизведение

```sh
npx tsx scripts/pipecat-dsm-fixture.ts
docker exec -i salesboost-pipecat-pipecat-1 python -c 'import sys; from pathlib import Path; Path("/tmp/probe_dialogue_state.py").write_text(sys.stdin.read())' < apps/pipecat-hypothesis/probe_dialogue_state.py
docker exec -i salesboost-pipecat-pipecat-1 python -c 'import sys; from pathlib import Path; p=Path("/tmp/dsm-fixture.json"); p.write_text(sys.stdin.read()); p.chmod(0o600)' < storage/pipecat-benchmarks/dsm/fixture.json
docker exec -e LOGURU_LEVEL=ERROR -e PYTHONPATH=/app salesboost-pipecat-pipecat-1 python /tmp/probe_dialogue_state.py --fixture /tmp/dsm-fixture.json --runs 5
```

Скрипт работает в `/tmp` существующего контейнера и не перезапускает сервис. Полные ответы, usage и медианы сохраняются в `/data/logs/dsm-<UUID>.json`, mode 600.
