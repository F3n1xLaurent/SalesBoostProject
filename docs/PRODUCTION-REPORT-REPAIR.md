# Локальная замена отчётов через диагностический токен

`npm run report:prod` получает исходные данные по HTTPS, запускает актуальную
локальную генерацию и отдельно публикует готовый отчёт. Используются существующие
`PROD_DIAGNOSTIC_BASE_URL` и `PROD_DIAGNOSTIC_TOKEN`, соответствующий серверному
`DIAGNOSTIC_EXPORT_TOKEN`. SSH и доступ к Docker с локальной машины не нужны.
Поддерживаются обычные звонки, demo и тренировки; существующий готовый отчёт
также можно заменить.

## Однократная установка

Новые HTTP-ручки нужно один раз развернуть на сервере. После этого исправления
генератора можно запускать локально и публиковать результат без нового деплоя
и перезапуска. Для механизма замены не нужна отдельная миграция.
Исправления интерфейса или серверной логики чтения требуют обычного деплоя.

В локальной `.env` уже используются:

```dotenv
PROD_DIAGNOSTIC_BASE_URL=https://app.salsa-sales.ru
PROD_DIAGNOSTIC_TOKEN=<существующий диагностический секрет>
```

На сервере тот же секрет задан в `DIAGNOSTIC_EXPORT_TOKEN` (минимум 32 символа).
Он теперь разрешает и узкие операции замены/отката отчётов. Старый диагностический
GET остаётся только для чтения. Авторизация новых ручек также только через
`Authorization: Bearer ...`; браузерная сессия суперадмина её не заменяет.
Токен не сохраняется в артефактах, URL или квитанциях. Перенаправления запрещены.

Для локальной генерации нужны зависимости проекта и локальные настройки
AI-провайдера. Ключи и настройки модели с прода команда не скачивает.

## Использование

1. Скачать данные без вызова модели и изменения прода:

   ```sh
   npm run report:prod -- fetch call 1147
   ```

   Вместо номера допустим UUID. Для тренировки:
   `npm run report:prod -- fetch trainer <ID>`.
   Команда выведет `folder` — приватную папку со снимком исходных данных и
   идентификатором операции. По умолчанию это игнорируемая Git папка
   `storage/production-report-repairs`. Корень можно изменить через
   `REPORT_REPAIR_OUTPUT_DIR`.

2. Сформировать отчёт текущим локальным кодом:

   ```sh
   npm run report:prod -- generate "<folder>"
   ```

   Используются локальные модель и ключи, с обычным расходом API. Прод не меняется.
   Повтор команды продолжает `checkpoint.json`, сохраняя успешные примеры и
   проверки. Неопределённые или отклонённые примеры не допускаются к публикации.
   Для отдельного черновика: `npm run report:prod -- generate "<folder>" --draft /path/to/report.json`.
   Результат — `report.json`; метаданные с хешем — `generation.json`;
   ответы этапов — `trace-*.json`.

3. Проверить результат и загрузить его:

   ```sh
   npm run report:prod -- publish "<folder>"
   ```

   В оценке заменяется только `unified_call_report`. Исходные баллы, чек-лист и
   расшифровка сохраняются. Связанная запись плана получает тот же отчёт.
   Снимается только ошибка `REPORT_GENERATION_FAILED`; соответствующая
   неуспешная задача отчёта завершается. Остальные ошибки сохраняются.

   Сервер проверяет неизменность снимка, итоговый балл, полноту примеров,
   их хеши и независимые подтверждения с цитатами. Если за время локальной работы
   изменились исходные данные, отчёт, условия, каталог или очередь, вернётся
   HTTP 409 без замены. При активной обработке публикация также запрещена.
   В случае конфликта скачайте новый снимок. Ручная правка `report.json` после
   генерации требует повторной проверки через `generate --draft`.

4. Проверить состояние, особенно после обрыва связи:

   ```sh
   npm run report:prod -- status "<folder>"
   ```

   `published` — данные совпадают с опубликованными; `original` — исходное
   состояние; `changed` — данные изменились; `not_published` — резервная запись
   операции отсутствует. После ошибки связи сначала проверьте состояние.

5. При необходимости вернуть исходный отчёт:

   ```sh
   npm run report:prod -- rollback "<folder>"
   ```

   Откат разрешён, пока опубликованные данные не изменились. Он восстанавливает
   прежний отчёт, ошибки, приватный черновик и изменённые поля связанной задачи.
   Для следующей замены выполните новый `fetch` с новым идентификатором операции.

## HTTP-контракт

Все ручки требуют диагностический bearer и отвечают с `Cache-Control: no-store`:

- `GET /api/internal/diagnostics/reports/{call|trainer}/{id}` — снимок и fingerprint.
- `POST /api/internal/diagnostics/reports/{call|trainer}/{id}` — публикация;
  JSON: `{operationId, fingerprint, report}`. Передать произвольную оценку или SQL нельзя.
- `GET /api/internal/diagnostics/report-operations/{operationId}` — состояние операции.
- `POST /api/internal/diagnostics/report-operations/{operationId}/rollback` — откат.

Без настроенного серверного токена ручки отключены (404), неверный токен — 401,
неверный запрос — 400, изменившиеся данные — 409, непригодный отчёт — 422.

## Хранение

Перед коммитом сервер сохраняет исходное и новое состояние в
`/data/report-replacements/<operationId>.json` (каталог `0700`, файл `0600`).
Это постоянный volume стандартной production-конфигурации. Каталог можно
переопределить через `REPORT_REPLACEMENT_BACKUP_DIR`; в DEV используется
`storage/report-replacements`. При ошибке резервирования замена откатывается.

Сохраняйте локальную папку: она содержит снимок, отчёт, трассировку,
адрес назначения и квитанции, без токена. При аварийном завершении локальной
генерации может остаться `generation.lock`: проверьте PID и удалите файл только
после завершения процесса. Расход локальной генерации учитывается локально,
в таблицы расходов прода автоматически не переносится.

Тесты `productionReportBridge.test.ts` и `diagnosticReportReplacementHttp.test.ts`
используют временную SQLite, подменённый HTTP-клиент и модель. Реальные продовые
данные и платные API не используются.
