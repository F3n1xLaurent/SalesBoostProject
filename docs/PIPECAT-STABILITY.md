# Стабилизация Pipecat после разбора звонка и плана Salsa

Версия `runtimeRevision=pipecat-stability-1`. Изменения относятся к изолированной гипотезе 3. Production-провайдеры, планы и гипотеза 2 не переключались.

После следующего телефонного теста выпущена `pipecat-stability-2`: если финальная реплика модели уже отправлена в TTS, второе прощание не добавляется; TTS-метрики привязаны к response ID. Проходят 54 Python-теста. Разбор и границы проверки — [PIPECAT-CALL-ad66f7f4.md](PIPECAT-CALL-ad66f7f4.md).

## Поведение

- Служебные инструкции выбранного промпта адаптируются для Pipecat. Противоречащий абзац `Finish call` заменён, ссылки на отсутствующие `skip_turn` и DTMF убраны. Бизнес-вопросы, легенда и данные плана сохраняются. Имя клиента фиксируется для всей сессии с учётом заданного имени или пола профиля.
- Realtime сначала настраивает сессию и инструменты, но не генерирует приветствие до первой реплики собеседника. При этом не создаётся фиктивный активный TTS-ответ, из-за которого первое «алло» раньше могло считаться перебиванием.
- Память звонка содержит этап, имя, последний подтверждённый вопрос, факты с цитатами и сведения о прерванных ответах. Значения фактов должны дословно входить в цитату последних реплик сотрудника. Время не преобразуется в числа и не пересчитывается моделью. Это подтверждение источника текста, не гарантия семантической истинности факта.
- В разговоре доступны `get_call_context`, `remember_call_fact`, `prepare_end_call`. Условия завершения проверяет код. При согласовании визита нужны сохранённые день и время. При отказе, перезвоне или voicemail нужна цитата. Исчерпанный разговор может завершиться без договорённости о визите.
- После принятого `prepare_end_call` дальнейшая генерация не запрашивается. Транспорт формирует одно короткое прощание; для визита или перезвона использует сохранённую дословную договорённость. Оно отправляется в тот же ElevenLabs TTS. Модель не получает прямой инструмент `end_call`. Отбой ждёт подтверждения **этого финального ответа**, а не старого `last_ack` от предыдущего аудио. Для voicemail речь не генерируется.
- При вероятном завершении текст перед инструментом удерживается. Если вызван инструмент, служебное сопровождение не передаётся в TTS. Это отдельная защита финала, не буферизация всех обычных ответов. Маршрутизация возможного завершения по тексту STT — узкая эвристика; поздняя/ошибочная STT и необычные формулировки требуют проверки на звонках.
- Новая содержательная реплика во время прощания возвращает инструменты и этап диалога. Короткие реакции по прежней политике не прерывают аудио.

## Перебивание и контекст

`DeliveryLedger` связывает response ID, TTS context ID и Voximplant tag. Запись локально выданного слова не равна подтверждению телефонии. Полностью воспроизведённым считается ответ, у которого закончены генерация и TTS и подтверждены все известные сегменты.

При прерывании незаконченной озвучки соответствующие assistant items удаляются из серверного контекста перед следующим запросом, даже если генерация давно закончилась и `_current_assistant_response` уже `None`. В `CALL_STATE.delivery_note` сохраняются подтверждённые сегменты и **приблизительный** локальный текст с предупреждением о точности. Сгенерированный непрозвучавший вопрос не остаётся обычной целой репликой assistant. Полностью подтверждённые ответы не удаляются и не помечаются отменёнными. Поздний `response.done` не восстанавливает удалённый item в локальном зеркале.

Это не пословная телефонная расшифровка: Voximplant даёт подтверждения сегментов, а не каждого услышанного слова. Точный слышимый префикс нужно сверять с записью. Для Gemini обычный контекст остаётся локальным; ремонт серверных conversation items относится к Realtime.

## Подключения и задержки

После preflight, **до набора номера**, открывается рабочий WebSocket ElevenLabs с тем же голосом, моделью и PCM16 mono 16 кГц. Регистрируется пустой контекст, проверяется ping; тестовый звук в линию не отправляется. Это же соединение затем получает реальный Pipecat TTS, а не ещё один холодный сокет. Во время ожидания оно поддерживается keepalive. При ошибке до набора, занятом/неотвеченном звонке и истечении срока ожидания ресурсы освобождаются.

Подготовка TTS имеет две ограниченные попытки. Потерянное соединение при передаче не считается готовым. Runtime-подключения TTS и Realtime также имеют ограниченное восстановление; исчерпание попыток приводит к диагностируемой ошибке. Это не устраняет нестабильность сети и не гарантирует успешного подключения каждого звонка.

Для Realtime добавлены `response_first_text_ms` и `response_total_ms`, привязанные к конкретному request/response ID. Повторный ответ не измеряется от старого запроса того же turn. Сводка показывает количество образцов, медиану и p95; выборки менее 20 отмечены как малые. Длительность проигрывания длинной фразы не считается задержкой получения ответа. Исходные события остаются в полном журнале.

## Общие сценарии и воспроизведение проверок

CLI импортирует сценарии и версию фикстур прямо из `src/voice/realtimeRegressionScenarios.ts`, не копируя и не меняя гипотезу 2:

```bash
npm run pipecat:regression -- --synthetic --provider openai --scenarios introduction,callback --warm-tts
npm run pipecat:regression -- --synthetic --provider gemini_proxyapi --scenarios introduction,callback
npm run pipecat:regression -- --synthetic --provider openai --scenarios callback --audio-tts
```

Без `--scenarios` доступны все 10 общих фикстур. `--synthetic` использует искусственные промпт и предмет обращения, без CRM-контекста. Голос берётся из существующей конфигурации ElevenLabs. Отчёты `pcr-*.json` и журналы с обычными `pc-...` ID сохраняются в volume. Результаты доступны для сравнения по провайдеру и версии фикстур.

По умолчанию вход текстовый, ответ проходит через реальные сервисы Pipecat и Function Calling. Вариант `--audio-tts` добавляет реальный ElevenLabs, PCM и сериализатор Voximplant с **имитированными** ACK. В диагностике такие callbacks помечены `simulation=true`. Ни один режим не набирает номер. Эти прогоны не доказывают качество STT, VAD, Smart Turn, настоящего barge-in, телефонных буферов или произношения. Семантические пункты помечены `review`, а не автоматически `pass`; существующий AI judge к этому CLI пока не подключён. Длинные реплики из нескольких частей объединяются для текстовой проверки, внутренние акустические паузы не имитируются.

Режим `--id pc-<UUID>` позволяет выбрать реальный исходный контекст, но в этой работе такой API-прогон был отклонён автоматическим контролем как повторная передача бизнес-данных внешним сервисам. Выполнены только синтетические проверки.

## Проверено и что остаётся измерить

52 Python-теста покрывают регистрацию/завершение инструментов, цитаты, условия визита и перезвона, подготовку и повторное использование сокета, отказ до набора при неготовом TTS, ограничение попыток Realtime, ремонт контекста, привязку задержанного TTS к исходному response ID и защиту от старого playback ACK. Также проходят 32 TS-теста, `tsc`, frontend build.

Живая синтетическая проба подготовленного TTS дала 130560 байт PCM16 mono 16 кГц и первое аудио через 355,38 мс от запуска прогретого TTS-пробника; повторное использование соединения подтверждено. Это один образец без телефонии, не p50/p95.

Сценарии introduction/callback выполнены на OpenAI и Gemini ProxyAPI. При разработке тесты выявили лишние попытки `end_call` и мета-фразы; поэтому финал перенесён в транспорт. В одной интеграционной аудиопробе был timeout подключения OpenAI; добавлено ограниченное восстановление. Историю этой неудачи не следует исключать из оценки устойчивости.

Интеграционная аудиопроба `pcr-974f0002-77fd-40f2-8038-44f8d733f42d` успешно выдала 281600 байт PCM, одно прощание «Хорошо, перезвоню завтра после десяти утра. До свидания.» и запросила отбой после имитированного ACK финального сегмента. Журнал — `pc-fe6a4ac7-9d1a-4f3d-b1b0-c5ac311ecc7f`. Перед этим также зафиксированы два timeout подготовки ElevenLabs; бюджет подготовки до набора увеличен, число попыток осталось ограниченным. Отчёты и ограничения измерений — [PIPECAT-STABILITY-PROBES.json](PIPECAT-STABILITY-PROBES.json).

Повтор финальной сборки: `pcr-8b6f85ab-0113-439a-ad04-1d6cdae8cf00`, журнал `pc-63d106ba-6666-47e5-8439-aa10a590f0fa`, 294400 байт PCM, одно такое же прощание, `finishRequested=true`, `simulatedHangup=true`, ошибок транспорта нет. Служебные пробы скрыты из обычной истории звонков; по ID доступны как прежде, приватный `/sessions?include_probes=true` включает их в список.

Цель медиана ≤1,5 с / p95 ≤2,5 с **пока не подтверждена**. Следующий телефонный тест должен проверить: первый ответ без стартовой тишины, длинную паузу перед ответом на вопрос, короткие «угу», полноценное перебивание перед окончанием вопроса, уточнение во время прощания и отбой сразу после фактического финального аудио. Для следующего разбора достаточно ID из гипотезы 3.
